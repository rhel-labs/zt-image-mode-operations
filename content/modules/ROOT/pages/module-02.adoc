= Repurposing a bootc host

In addition to simplifying updates and providing native rollback, operating RHEL in image mode also makes it simple to quickly change the purpose of a running system.

The `switch` operation allows administrators to change the system software to a different image, while keeping local system configuration and data intact.

In this lab we'll explore this feature as well as expand on the idea of standardized builds and derived images.

== Working with the Developer's Application

=== Introducing the Application

While you've been building a secure baseline image with compliance policies and management tools, the development team has been working on a new web application. They've created a Python Flask service called `python-hostinfo` that displays system information, and they've built it as a bootc image for their proof of concept.

Their application repository has been cloned to your build host at `~/bootc-version`. Let's take a quick look at what's there:

[source,bash,role="execute",subs=attributes+]
----
ls ~/bootc-version
----

The repository contains:
- **Containerfile** - Builds the application as a bootc image from the Red Hat `rhel-bootc:10.1` base
- **app.py** and **helpers.py** - The Flask web application
- **info-app.service** - systemd service definition for the application
- **info-app.conf** - nginx reverse proxy configuration
- **nginx_connect_flask_sock.te** - SELinux policy module for nginx/Gunicorn communication
- **static/** and **templates/** - Web assets
- **requirements.txt** - Python dependencies

The application stack uses Python Flask with Gunicorn as the application server, fronted by nginx as a reverse proxy, all managed by systemd services.

=== The Problem Report

The developers report an issue: their image works perfectly when provisioning a fresh machine with `bootc-image-builder`. However, when they tried to **switch** an existing running system to their application image (to save time and reuse infrastructure), nginx fails to start with errors about missing `/var` directories.

They weren't sure if this was related to the RHEL version difference (they tested on RHEL 9.6) or something else about the image mode deployment model.

2. **Integrate** their application with your secure baseline image
3. **Optimize** the build using container best practices

This will demonstrate how to work with derived images and combine work from different teams (operations baseline + developer application = production-ready image).

== Testing the developers bug report

While testing their proof of concept, the developers found that the image they created worked fine when a machine was newly installed.
To help save time, they wanted to repurpose a few other image mode machines instead of requesting brand new infrastructure.
When they switched the running machine, the application wouldn't start.
They only had a RHEL 9.6 host to test, and they weren't sure if moving to RHEL 10.1 was part of the problem.

Change to the application git repository with the bootc Containerfile, cloned onto the build host.
[source,bash,role="execute",subs=attributes+]
----
cd ~/bootc-version
----

First, let's add linting and then build a fresh copy to test the switch on our own existing image mode host.
[source,bash,role="execute",subs=attributes+]
----
nano Containerfile
----

Add the following line as the last instruction in the Containerfile.
We always want linting to be the final step in a build.
[source,dockerfile,role="execute",subs=attributes+]
----
RUN bootc container lint
----

The linter is designed to issue warnings about potential problems and will error and stop the build if there is something that would stop an image mode host from operating. 
Some warnings are harmless, but others could point to issues with certain types of operations during the lifetime of a host.

== Switch and test the image

_Change to the tab labeled "Bootc VM"_

You saw earlier how `bootc` tracks the image in the registry to find updates.
To change to a different image, use the `bootc switch` command to provide a different image specification.
We'll use it to change into the testing image we just pushed to the registry.
[source,bash,role="execute",subs=attributes+]
----
sudo bootc switch registry-{guid}.{domain}/app-test
----

From an output perspective, a switch looks the same as an update. There's a new deployment that's been staged and prepared for the next boot, but the image reference is completely different.
